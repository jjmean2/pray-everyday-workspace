# 정합성 감사 체크리스트

설계 문서끼리, 그리고 문서와 코드가 서로 다른 말을 하는 곳(불일치)을 스코프 전체에서 찾는 절차다. 리뷰 체크리스트가 "이번 변경"을 본다면, 감사는 "스코프 전체"를 본다.

## 언제 하나

- 큰 설계 변경을 마친 뒤
- `design-harness check`의 안내(연결되지 않은 요구, 링크되지 않은 ADR, 남은 notes)가 쌓였을 때
- 마지막 감사로부터 `design-harness.toml`의 `audit_days`(기본 90일)가 지났을 때. `check`가 알려 준다

## 절차

1. `design-harness check`를 실행하고 결과를 읽는다.
2. 감사할 스코프마다 `design-harness context --notes <경로>`로 문서를 모두 읽는다. 링크된 ADR도 읽는다.
3. 아래 항목을 점검하고, 찾은 것을 둘로 나눈다.
   - **기록 정정**: 바로 고친다
   - **결정 필요**: 충돌하는 자리에 불일치 표시를 남기고 사람에게 보고한다
4. 기록 정정은 각각 제목이 `불일치 복구:`로 시작하는 커밋으로 남긴다. 감사를 마치면 제목이 `정합성 감사:`로 시작하는 커밋을 마지막에 따로 둔다. 고친 것이 없으면 빈 커밋(`git commit --allow-empty`)으로 남긴다.

## 점검 항목

- **문서끼리의 충돌**: ARCHITECTURE, REQUIREMENTS, CONVENTIONS가 같은 주제를 다르게 말하는가
- **스코프 위반**: 하위 스코프의 문서가 상위 규칙을 뒤집는가
- **중복**: 같은 규칙이나 결정이 두 곳에 있어 어긋날 수 있는가
- **요구와 설계**: 요구사항이 바뀌었는데 그것을 감당하는 설계 절의 가정과 한계가 그대로인가
- **문서와 ADR**: Accepted ADR의 결정이 현재 상태 문서에서 사라졌는가(그렇다면 ADR을 대체·폐기한다). 현재 문서의 중요한 결정에 이유(ADR)가 없는가
- **문서와 코드**: 코드의 구조가 현재 상태 문서와 다른가. 코드가 문서에 없는 설계 결정을 내렸는가
- **notes**: 반영도 폐기도 안 된 채 오래 남아 사실상 규칙처럼 쓰이는 항목이 있는가
- **남은 표시와 레거시**: 해결되지 않은 불일치 표시, 끝났는데 남은 레거시 행이 있는가

## 나누는 기준

| 구분 | 예 | 누가 |
|---|---|---|
| **기록 정정** | 깨진 링크, 근거(ADR, 커밋, 사람의 지시)가 분명한 반영 누락, 중복 제거, 오래된 notes 정리 | 에이전트가 바로 고친다. 커밋 제목을 `불일치 복구:`로 시작한다 |
| **결정 필요** | 두 문서가 다른 결정을 말한다. 코드와 문서 중 어느 쪽이 맞는지 근거가 없다 | 표시를 남기고 보고한다. 사람이 정하면 문서를 고치고 표시를 지운다 |

애매하면 결정 필요로 분류한다.

# 설계 리뷰 체크리스트

변경된 코드와 문서가 현재 상태 문서에서 벗어나지 않았는지 검토하는 절차다. 어떤 에이전트나 사람이 리뷰하든 이 문서를 따른다.
버그나 코드 스타일이 아니라 **현재 설계와의 정합성**만 본다. 리뷰어는 수정하지 않고 보고만 한다.

## 절차

1. 리뷰 대상 diff를 확인한다. 별도 지정이 없으면 `git diff HEAD`로 커밋되지 않은 변경을 본다.
2. 변경된 각 경로에 대해 `design-harness context <경로>`를 실행하고, 출력된 현재 상태 문서(ARCHITECTURE, REQUIREMENTS, CONVENTIONS)를 모두 읽는다. 해당 스코프의 `notes/architecture.md`에 남은 타협도 읽는다.
3. `design-harness check`를 실행해 형식과 연결 검사 결과를 참고한다.
4. 아래 항목을 점검한다.

구속력은 현재 상태 문서에만 있다. ADR은 이유를 확인할 때만 읽는다. archive는 읽지 않는다.

## 점검 항목

- **경계 위반**: 모듈 의존 방향이나 공개 인터페이스 규칙을 어겼는가
- **컨벤션 위반**: `CONVENTIONS.md`의 규칙을 어겼는가
- **스코프 위반**: 하위 스코프의 변경이 상위 스코프의 규칙을 뒤집는가
- **불변식 위반**: 불변식을 깨뜨릴 수 있는 코드 경로가 생겼는가
- **숨은 우회**: 특정 케이스만을 위한 분기, 플래그, 중복 상태, 동기화 코드가 생겼는가
- **가정 위반**: 관련 설계 절의 "전제한 것"이 이 변경으로 더 이상 참이 아니게 되었는가, "감당하지 못하는 것"을 하게 되었는가
- **추측한 설계**: 현재 상태 문서가 정하지 않은 설계 판단을 코드가 스스로 내렸는가
- **레거시 모방**: "이행 중인 레거시"에 적힌 패턴을 새 코드가 따라 했는가
- **반영 누락**: 코드가 바뀌었는데 현재 상태 문서(설계 절, 감당하는 요구, 가정과 한계)가 그대로인가. 요구사항이 바뀌었는데 그 절을 링크하는 설계 절을 다시 보지 않았는가
- **타협 누적**: 이번 변경 영역의 설계 절에 notes의 타협이 이미 쌓여 있는가
- **기록 누락**: 이유를 다시 보고 싶을 만한 결정인데 ADR이 없는가
- **불일치 표시**: 이번 변경이 `불일치 (결정 필요)` 표시가 있는 부분에 기댔는가, 해결했는데 표시를 남겼는가
- **정리 누락**: 끝난 레거시 행, 반영한 notes 항목, 해결된 타협이 남아 있는가

## 보고 형식

발견마다:

- **위치**: 파일과 줄
- **어긋나는 설계 요소**: 설계 절, 컨벤션, 불변식, 또는 문서 불일치
- **내용**: 무엇이 어떻게 어긋나는가
- **판단**: `문서만 갱신하면 됨` / `코드를 설계에 맞게 고쳐야 함` / `설계 재검토 필요` / `레거시 정리 필요`

`설계 재검토 필요`가 하나라도 있으면 맨 위에 따로 알리고, 영향 범위와 관련 설계 절을 함께 적는다.
문제가 없으면 무엇을 확인했는지 짧게 적는다.

# 설계 문서 체계 (design-harness)

사람과 에이전트가 함께 쓰는 설계 문서의 운영 절차다. 항상 지켜야 하는 핵심 규칙은 [AGENTS.md](../../AGENTS.md)의 design-harness 블록에 있고, 이 문서는 절차의 세부를 다룬다.
이 문서는 design-harness가 문서 버전 0.1의 구조로 부트스트랩했다. 프로젝트가 소유하므로 고쳐도 된다.

## 한눈에

1. `notes/`에서 요구사항, 아키텍처, 컨벤션을 정하며 기억할 것을 적는다
2. 그 결과를 `REQUIREMENTS.md`, `ARCHITECTURE.md`, `CONVENTIONS.md`의 현재 상태로 반영한다. **구현은 이 현재 상태만 따른다**
3. 그중 결정 이유를 다시 보고 싶을 만한 것은 번호를 붙인 ADR로 남긴다. ADR은 불변이고, 대체되거나 폐기되면 archive로 옮긴다

## 문서의 세 층

| 층 | 문서 | 구속력 | 수명 |
|---|---|---|---|
| **현재 상태** | `REQUIREMENTS.md`(무엇이 필요한가), `ARCHITECTURE.md`(어떻게 생겼나), `CONVENTIONS.md`(구현할 때 지킬 설계 수준의 규칙) | 있음. 구속력은 여기에만 있다 | 계속 다시 쓴다. 바뀌거나 폐기된 내용은 지우고, 이력은 git에 둔다 |
| **결정 기록** | `decisions/NNNN-제목.md`(ADR) | 없음. 이유의 기록 | 영구. 불변이고 상태만 바뀐다. 대체·폐기되면 `archive/decisions/` |
| **작업 메모** | `notes/` | 없음. 정하는 일의 입력 | 임시. 현재 상태에 반영하면 지운다 |

현재 상태 문서와 ADR은 `notes/`와 archive를 링크하지 않는다. notes는 지워지고, archive는 현재 설계가 아니기 때문이다.

## 두 가지 일

| 일 | 무엇을 하나 | 읽는 것 | 쓰는 것 |
|---|---|---|---|
| **정하는 일** | 요구사항, 아키텍처, 컨벤션을 쓰고 고친다 | notes, 현재 상태 문서, ADR (`design-harness context --notes <경로>`) | 현재 상태 문서, ADR, notes |
| **구현하는 일** | 코드를 쓴다 | 현재 상태 문서만 (`design-harness context <경로>`). 이유가 궁금하면 링크된 ADR | 코드. 구현 중 타협한 지점은 notes에 남긴다 |

같은 에이전트가 두 일을 다 해도 된다. 일의 종류에 따라 읽는 것이 다르다.
구현하는 일에서 현재 상태 문서가 정하지 않은 설계 판단이 필요해지면, 추측해서 채우지 않고 멈춘다. 그 판단은 정하는 일로 넘어간다.

## 현재 상태 문서

모두 현재 유효한 것만, 결정한 순서가 아니라 의미 순서로 체계적으로 쓴다. 식별자를 붙이지 않는다. 문서 안에 "예전에는 X였다"를 쓰지 않는다.

### REQUIREMENTS.md

이 스코프가 지금 충족해야 하는 것을 영역별 절(`##`, `###`)로 나눠 문장으로 쓴다. 아직 정리 중이거나 보류한 요구는 여기 두지 않고 notes에 둔다. 하위 시스템 스코프는 생략할 수 있다.

### ARCHITECTURE.md

처음 읽는 사람과 에이전트가 여기서 시작한다. 현재 상태, 개요(조감도, 코드 지도), 범위를 먼저 두고, 이어서 설계를 의미 단위의 절로 서술한다. 끝에 불변식과 이행 중인 레거시를 둔다. 루트 스코프는 하위 스코프 목록도 둔다.

설계 절에는 그 절이 무엇을 위해 있고 언제 다시 봐야 하는지를 정해진 꼴로 적는다.

```markdown
## 저장소 동기화

(이 부분이 어떻게 생겼는지 서술)

**감당하는 요구**: [오프라인 기록](REQUIREMENTS.md#오프라인-기록), [기기 간 동기화](REQUIREMENTS.md#기기-간-동기화)

**가정과 한계**
- 전제한 것: (이 설계가 성립하려면 참이어야 하는 것)
- 감당하지 못하는 것: (이 설계로는 안 되는 것)
- 다시 볼 계기: (이 일이 생기면 설계를 다시 본다)

**이유**: [ADR-NNNN](decisions/NNNN-로컬-우선-저장소.md)
```

- **감당하는 요구**는 요구사항 절을 링크한다. 요구사항이 바뀌면 그 절을 링크하는 설계 절을 찾아 가정과 한계를 다시 본다. 요구사항 절의 이름이 바뀌거나 지워지면 링크가 깨지고 `check`가 알려 준다
- **가정과 한계**는 새 요구를 분석하는 기준이다
- **이유**는 그 설계를 정한 ADR이 있으면 링크한다. 없어도 된다

**이행 중인 레거시**: 아직 코드에 남았지만 현재 설계가 아닌 것이다. 표로 두고 모방하지 않는다. 정리가 끝나면 행을 지운다.

### CONVENTIONS.md

구현할 때 지킬 설계 수준의 규칙이다(예: "DB 접근은 repository 모듈로만"). lint와 formatter로 강제할 수 있는 규칙은 그 도구에 둔다. 에이전트의 작업 절차는 `AGENTS.md`에 둔다. 이유를 다시 보고 싶은 규칙은 ADR을 링크한다.

### 링크

- 다른 현재 상태 문서의 절은 `파일#앵커`로 링크한다. 앵커는 제목을 소문자로 바꾸고 공백을 `-`로, 문장 부호를 뺀 것이다(GitHub 방식)
- `check`는 깨진 파일 링크와 앵커, notes와 archive로의 링크, 어떤 설계 절의 **감당하는 요구**에도 연결되지 않은 요구사항을 알려 준다. 요구사항 단위는 자기 본문이 있는 절이고, 그 절이나 위 절이 링크되면 연결된 것으로 본다

## notes/

정하는 일의 작업 메모다. 구속력이 없고 구현의 근거가 되지 않는다.

| 파일 | 담는 것 |
|---|---|
| `notes/requirements.md` | 받은 요구, 정리 중인 요구, 아직 반영하지 않았거나 보류한 요구 |
| `notes/architecture.md` | 열린 질문, 진행 중인 판단, 인수인계, 구현 중 타협한 지점 |
| `notes/conventions.md` | 정하는 중인 규칙, 검토할 관행 |

- 형식은 자유다. 임시 번호를 붙여도 되지만, 그 번호는 현재 상태 문서나 ADR에서 쓰지 않는다
- **아직 정하지 않은 것**은 열린 질문으로 notes에 둔다. 현재 상태 문서에는 정한 것만 쓴다. 구현은 현재 상태 문서가 정하지 않은 판단에서 멈추므로, 정하지 않은 것을 추측해 구현하는 일이 생기지 않는다
- `check`는 notes 파일마다 최상위 목록 항목(`- `로 시작하는 줄)의 수를 남은 항목으로 알린다. 주석(`<!-- -->`)과 코드 블록은 세지 않는다
- 현재 상태 문서에 반영하면 그 항목을 지운다. 지운 기록은 git에 남는다
- 세션이나 사람이 바뀌어도 이어지도록 커밋한다
- **타협 기록만 꼴을 정한다**: `- [타협] YYYY-MM-DD 무엇을 어떻게 타협했나 (관련: [절 제목](../ARCHITECTURE.md#앵커))`. 같은 설계 절에 열린 타협이 `design-harness.toml`의 `friction_threshold`(기본 3개) 이상 쌓이면 `check`가 재설계를 검토하라고 알린다. 해결되면 지운다

## ADR

### 언제 쓰나

결정 이유를 나중에 다시 보고 싶을 만한 아키텍처나 컨벤션의 결정을 남긴다. 예: 데이터 모델, 모듈 경계와 공개 인터페이스, 언어·프레임워크·외부 서비스 선택, 스코프 구조, 검토한 대안이 여럿이었던 결정.
작은 결정은 ADR 없이 현재 상태 문서를 고치고 커밋 메시지에 이유를 적는다. 작은 질문을 하나씩 ADR로 쌓지 않는다. notes에서 정리하다가 결정이 끝났을 때 큰 단위로 쓴다.

### 어떻게 쓰나

- 결정이 끝났을 때 `design-harness adr new "제목"`으로 만든다. 처음부터 `Accepted`다. 제안과 논의는 대화와 notes에서 한다
- 요약, 맥락, 결정, 검토한 대안을 한 쪽 안팎으로 쓴다. ADR만 읽어도 이해되게 쓰고 notes를 링크하지 않는다. 다른 ADR은 번호(`ADR-NNNN`)로만 적고 링크하지 않는다. 대체되면 링크가 끊기는데 ADR 본문은 고치지 않기 때문이다
- 같은 결정을 현재 상태 문서에 반영하고, 해당 절의 **이유**에 링크한다

### 상태와 archive

| 상태 | 뜻 | 위치 |
|---|---|---|
| `Accepted` | 결정의 일부라도 현재 상태에 반영돼 있다 | `decisions/` |
| `Superseded by ADR-NNNN` | 다른 결정으로 전부 대체됐다 | `archive/decisions/` |
| `Deprecated` | 대체 없이 폐기됐다 | `archive/decisions/` |
| `Rejected` | 이전 규약(Proposed가 있던 때)에서 기각된 기록. 새로 쓰지 않는다 | `archive/decisions/`에만 |

- 본문은 고치지 않는다. 상태 줄만 바뀐다
- 전부 뒤집히면 `design-harness adr supersede <옛 번호> --by <새 번호>` 또는 `adr deprecate <번호>`로 상태를 바꾸고 archive로 옮긴다. 도구가 현재 상태 문서에서 그 ADR을 링크하는 곳을 남은 작업으로 알려 준다
- 일부만 바뀌면 새 ADR이 어느 부분을 바꾸는지 적고, 옛 ADR은 `Accepted`로 둔다. 진실의 출처는 현재 상태 문서다
- archive는 지우지 않는다. 같은 제안을 다시 꺼내기 전에 `design-harness adr list --all --grep <말>`로 확인한다. 그 밖에는 읽지 않는다

## 정하는 일의 절차

요구사항 변경, 구현 중 발견, 타협 누적, 요구사항은 그대로인 리팩터링 모두 같은 절차다.

1. **담는다**: 받은 요구나 질문을 notes에 적는다. 바로 정리되면 생략한다
2. **영향을 찾는다**: 바뀐 요구사항 절을 링크하는 설계 절(**감당하는 요구**)을 찾고, 그 절의 **가정과 한계**와 대조한다. 새 요구라면 가장 가까운 설계 절과 대조한다
3. **분류해 보고한다**
   - **적합**: 지금 설계로 된다 → 요구사항을 반영하고 진행한다
   - **확장**: 설계에 요소를 더하면 되고 가정은 유지된다 → 현재 상태 문서의 변경을 짧게 제시하고 진행한다
   - **재설계**: 가정이나 한계에 걸리거나 상위 스코프와 충돌한다 → 사람과 정한다. 정할 때까지 구현하지 않는다
   - 애매하면 더 무거운 쪽으로 분류한다
4. **반영한다**: 정해지면 현재 상태 문서를 먼저 고친다. 다시 이유를 보고 싶을 결정이면 ADR을 남긴다. 옛 설계를 따르던 코드가 남으면 "이행 중인 레거시"에 적는다
5. **구현하고 정리한다**: 레거시를 지우고 그 행을 지운다. 반영한 notes 항목과 해결된 타협을 지운다

사람이 현재 상태 문서를 직접 고쳐도 된다. 그때는 에이전트에게 다른 문서와 맞는지 봐 달라고 요청한다.

## 구현하는 일과 멈춤

멈춤 신호(`AGENTS.md`)가 보이면 우회하지 않고 멈춘다. 멈추는 것은 실패가 아니다. 보고할 것:

1. 어떤 신호가 걸렸고, 어느 설계 절이나 컨벤션과 충돌하는지
2. 우회하면 어떤 코드가 되는지 (선택지 A)
3. 설계를 바꾸면 어떻게 되는지 (선택지 B), 영향 범위와 어느 스코프의 변경인지
4. 어느 쪽을 추천하는지와 그 이유

멈출 정도는 아닌 타협은 notes에 `[타협]`으로 남긴다.

## 불일치

설계 문서끼리, 또는 문서와 코드가 서로 다른 말을 하는 것을 불일치라고 한다. 예: ARCHITECTURE는 "충돌하면 서버 기록을 남긴다"인데 CONVENTIONS는 "로컬 기록은 버리지 않는다".

**찾기**: 형식(깨진 링크, 연결되지 않은 요구 등)은 `check`가 찾는다. 뜻이 부딪히는 것은 에이전트가 [정합성 감사](audit-checklist.md)로 찾는다. 구현이나 리뷰 중에 발견해도 된다.

**해결 전에 따를 것**: 추측하지 않는다.

1. 상위 스코프가 하위 스코프보다 앞선다
2. 현재 상태 문서가 ADR, notes, 코드보다 앞선다. 해결 전에는 문서를 따른다. 코드와 문서 중 어느 쪽을 고칠지는 근거가 없으면 사람이 정한다
3. 같은 수준의 현재 상태 문서끼리 충돌하면 이기는 쪽이 없다. 그 부분에 기대는 구현은 멈추고 보고한다

해결을 기다리는 불일치는 충돌하는 자리(현재 상태 문서)에 줄머리 인용(`>`)으로 이렇게 표시한다. 구현하는 쪽은 이 표시가 있는 부분에 기대는 구현을 하지 않는다.

```markdown
> **불일치 (결정 필요)**: 이 절은 충돌 시 서버 기록을 남긴다고 하지만, CONVENTIONS의 "로컬 기록은 버리지 않는다"와 맞지 않는다.
> 정해질 때까지 충돌 처리에 기대는 구현은 멈춘다. (발견: YYYY-MM-DD)
```

**고치기**

| 구분 | 예 | 누가 |
|---|---|---|
| **기록 정정** | 깨진 링크, 근거(ADR, 커밋, 사람의 지시)가 분명한 반영 누락, 중복 제거, 오래된 notes 정리 | 에이전트가 바로 고친다 |
| **결정 필요** | 두 문서가 다른 결정을 말한다. 코드와 문서 중 어느 쪽이 맞는지 근거가 없다 | 표시를 남기고 보고한다. 사람이 정하면 문서를 고치고 표시를 지운다 |

복구한 커밋의 제목은 `불일치 복구:`로 시작한다. 감사 중에 고친 것도 복구 커밋으로 따로 두고, 감사를 마치면 `정합성 감사:`로 시작하는 커밋(빈 커밋이어도 된다)을 마지막에 둔다. 이유를 다시 볼 만한 결정이었다면 ADR도 쓴다. 무엇을 어떻게 복구했는지는 `git log --grep "불일치 복구:"`로 찾는다.

**도구의 알림**: `check`는 남은 표시의 개수와 나이(`design-harness.toml`의 `inconsistency_days`, 기본 30일), 마지막 감사로부터 지난 기간(`audit_days`, 기본 90일. git 이력의 `정합성 감사:` 커밋으로 판단), 항목이 남은 채 오래 바뀌지 않은 notes(`notes_days`, 기본 30일)를 알린다. 시간과 git에 따른 알림은 경고와 안내일 뿐 오류가 아니고, `check`의 판정(오류 여부)에 들지 않는다. 불일치 표시의 나이는 문서 안의 발견 날짜로, 감사와 notes의 나이는 git 이력으로 센다.

## 스코프

스코프는 스코프 폴더를 가진 디렉터리다. 루트의 스코프 폴더는 시스템 전체다. 폴더 이름은 `design-harness.toml`의 `scope_dir`로 정하고, 저장소의 모든 스코프가 같은 이름을 쓴다. 이 프로젝트는 `architecture/`이다.

```
architecture/                      루트 스코프 (시스템 전체)
apps/web/architecture/             프로젝트 스코프
apps/web/src/sync/architecture/    하위 시스템 스코프
```

각 스코프 폴더: `ARCHITECTURE.md`(필수), `REQUIREMENTS.md`, `CONVENTIONS.md`, `notes/`, `decisions/`, `archive/decisions/`. 루트에는 이 규약(`harness/`)도 있다.

- **읽는 순서**: 루트부터 작업 경로를 포함하는 가장 가까운 스코프까지 차례로 읽는다. 상위 규칙은 하위에도 적용되고, 하위는 더할 수만 있다
- **만들 때**: 상위와 독립된 모델, 경계, 결정이 생길 때 `design-harness scope new <경로>`로 만들고, 루트 `ARCHITECTURE.md`의 스코프 목록에 등록한다. `ARCHITECTURE.md`가 `architecture_max_lines`(기본 400줄)를 넘으면 분리하라는 신호다
- **결정을 옮길 때**: 여러 스코프에 필요해지면 공통 상위로 올리고, 한 스코프에만 해당하면 그 스코프로 내린다
- **지울 때**: 코드가 사라지면 그 스코프 폴더도 지우고 루트 목록에서 뺀다. archive로 옮기지 않는다

### 스코프 폴더 이름 바꾸기

1. 모든 스코프 폴더를 새 이름으로 옮긴다(`git mv`)
2. `design-harness.toml`의 `[harness]`에 `scope_dir = "<새 이름>"`을 적는다
3. 부트스트랩 구조(이 문서, 체크리스트, 어댑터, 관리 블록) 안의 옛 경로를 고친다. `design-harness upgrade`가 판과 다른 파일로 알려 주는 목록과 맞춰 본다
4. `design-harness check`로 확인한다

## 하네스의 구성과 버전

| 구분 | 경로 | 규칙 |
|---|---|---|
| **부트스트랩 구조** | `architecture/harness/` 전체, `.claude/agents/design-reviewer.md` | `init`이 만들었고 프로젝트가 소유한다. 도구가 읽는 형식만 지키면 고쳐도 된다. `upgrade`가 새 판의 변경을 합친다 |
| **프로젝트 문서** | `design-harness.toml`, 현재 상태 문서, notes, ADR | 프로젝트가 쓴다. 도구는 명시적인 명령으로만 바꾼다 |
| **공동** | `AGENTS.md`, `.githooks/pre-commit` | `design-harness:begin`과 `design-harness:end` 사이가 하네스의 블록이다. 고쳐도 되지만 마커는 남긴다 |

### 문서 버전

`design-harness.toml`의 `harness.docs_version`(예: `"0.1"`)은 이 프로젝트가 따르는 부트스트랩 구조와 문서 형식의 판이다. 관리 블록의 마커(`begin v0.1`)도 이 값과 같아야 한다.

| 변경 종류 | 예 | 문서 버전 (1.0부터) | 기존 문서 |
|---|---|---|---|
| **형식 변경, 호환되지 않음** | 도구가 읽는 꼴의 삭제·이름 변경·의미 변경. 기존 문서가 새 `check`에서 오류가 되는 규칙 | major | `upgrade`의 마이그레이션 단계가 형식 부분을 옮긴다 |
| **형식 변경, 추가만 함** | 새 선택 키, 새 선택 꼴, 안내만 늘어나는 검사 | minor | 고치지 않는다 |
| **권장 구조 변경** | 템플릿의 새 절, 안내 문구 | minor | 고치지 않는다. 다음에 고칠 때 맞춘다 |
| **절차 변경** | 이 문서, 관리 블록, 체크리스트의 규칙 | minor | 고치지 않는다. 받은 뒤의 작업부터 적용한다 |

**0.x는 실험 단계다.** 1.0 전까지는 호환되지 않는 변경도 minor로 낸다(0.1 → 0.2). 깨진 부분은 `check`가 알려 주고 프로젝트가 직접 고친다. ADR 본문은 어떤 경우에도 마이그레이션하지 않는다.

### 도구 설치와 업그레이드

도구 코드는 프로젝트에 들어 있지 않다. Python 3.11 이상에서 `design-harness`를 PATH에 설치한다. 같은 문서 버전이면 그 버전을 지원하는 어느 릴리스로 검사해도 결과가 같다. 버전을 고정하고 싶다면 프로젝트가 쓰는 도구(mise 등)로 고정한다.

```sh
uv tool install git+ssh://git@github.com/jjmean2/design-harness.git@v<도구 버전>
design-harness --version                # 도구 버전과 지원하는 문서 버전
design-harness upgrade --dry-run        # 새 판으로 올릴 때 바뀔 파일
design-harness upgrade [--to 0.2]       # 문서 버전을 올린다
```

도구를 올리는 것과 문서 버전을 올리는 것은 따로다. `upgrade`는 부트스트랩 구조와 관리 블록을 판 사이에서 파일마다 3-way로 합친다. 프로젝트가 고친 부분은 남고, 겹치면 충돌 표시(`<<<<<<<`)를 남기고 종료 코드 1로 끝난다. 1.0 이후 major를 넘을 때는 마이그레이션 단계도 실행하고, 그 단계가 없으면 멈춘다. 대상 파일에 커밋하지 않은 변경이 있으면 멈춘다.

## 도구 피드백

규약이나 도구 자체의 불편(절차가 과했다, 규칙이 모호했다, 검사가 잘못 걸렸다, 필요한 출력이 없었다)은 설계 타협과 구분해서 남긴다.

- design-harness 이슈 트래커를 쓸 수 있으면 이슈로 올린다
- 쓸 수 없으면 `architecture/harness-feedback.md`에 한 줄 남긴다(선택 파일). 반영되면 지운다
- 피드백을 남겼더라도 도구가 업데이트되기 전까지는 현재 규약을 따른다

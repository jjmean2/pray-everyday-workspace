# 아키텍처 노트

아키텍처를 정하는 동안 기억할 것을 적는다. 구속력이 없고 구현의 근거가 되지 않는다.
`ARCHITECTURE.md`나 ADR에 반영하면 그 항목을 지운다. 형식은 자유이고 임시 번호를 붙여도 된다.

## 열린 질문과 진행 중인 판단

구현이나 논의가 그 지점에 닿으면 정한다. 정하기 전에는 ARCHITECTURE가 이것들을 정하지 않으므로, 기대야 하는 구현은 멈추고 보고한다.

- 동기화 구현 방식(직접 구현 또는 동기화 엔진)
- 앱 구현 방식: iOS와 Android 네이티브로 생각 중이다. 도메인과 동기화 로직을 플랫폼마다 구현할지, Kotlin Multiplatform 같은 공유 코어를 둘지는 앱을 시작할 때 정한다
- 동기화 규칙의 언어 중립 테스트 벡터. 네이티브 앱을 만든다면 필요하다
- 운영 환경에서 웹과 서버의 경로 구성(개발 중에는 Vite가 `/api`를 서버로 프록시한다)
- UI 컴포넌트 구성(Base UI/shadcn은 첫 화면을 만들 때 설정한다)
- 배포 대상(운영 DB는 관리형 PostgreSQL 방향)
- 응답 표시를 어디에 둘지(기도제목, 이어진 기도, 별도 기록)
- 노트 제목을 둘지, 기도한 시각을 사용자가 바꿀 수 있는지
- 동기화를 끄거나 로그아웃할 때 서버와 기기의 데이터 처리
- 커뮤니티 가입 방식(초대 링크 등)
- 카카오에서 받을 동의 항목(이메일은 사업자 인증이 필요하다)
- 비운 노트: 기존 노트의 메모와 기도제목을 모두 지우면 지금은 빈 노트로 저장된다. 빈 노트를 그대로 둘지, 비우면 삭제로 볼지 정한다. 2026-10-23 설계 리뷰에서 발견
- 지운 태그: 지운 태그를 같은 ID로 다시 저장하면 지금은 되살아나는데, 그사이 다시 저장된 노트와 기도제목에서는 그 태그가 이미 빠져 있어 결과가 레코드마다 다르다. 또 지운 태그를 걸러 낸 목록을 그대로 저장하면 바뀐 것이 없어도 버전이 오른다. 추천: 지운 태그는 되살리지 않고(같은 ID로 저장하면 404나 409), 저장할 때의 비교는 걸러 낸 값으로 한다. 2026-10-23 설계 리뷰에서 발견
- 태그 이름의 정규화: 웹은 앞뒤 공백을 잘라 내고 소문자로 같은 이름을 판단하는데, 서버는 자르지 않고 PostgreSQL의 lower()로 비교한다. 규칙(앞뒤 공백 제거, 대소문자 무시 등)을 정해 packages/domain에 두고 ARCHITECTURE에 적는다. 2026-10-23 설계 리뷰에서 발견
- 정렬 키의 서버 검증과 길이 한도: 명세의 패턴은 fractional-indexing의 키 형식보다 느슨해서, 다른 클라이언트가 형식에 맞지 않는 키를 저장하면 웹의 키 생성이 실패할 수 있다. 서버에서 형식을 검사할지, 키가 길이 한도(100자)에 닿으면 다시 매길지 정한다

# 아키텍처 노트

아키텍처를 정하는 동안 기억할 것을 적는다. 구속력이 없고 구현의 근거가 되지 않는다.
`ARCHITECTURE.md`나 ADR에 반영하면 그 항목을 지운다. 형식은 자유이고 임시 번호를 붙여도 된다.

## 열린 질문과 진행 중인 판단

구현이나 논의가 그 지점에 닿으면 정한다. 정하기 전에는 ARCHITECTURE가 이것들을 정하지 않으므로, 기대야 하는 구현은 멈추고 보고한다.

- 동기화 구현 방식(직접 구현 또는 동기화 엔진)
- 앱 구현 방식: iOS와 Android 네이티브로 생각 중이다. 도메인과 동기화 로직을 플랫폼마다 구현할지, Kotlin Multiplatform 같은 공유 코어를 둘지는 앱을 시작할 때 정한다
- 동기화 규칙의 언어 중립 테스트 벡터. 네이티브 앱을 만든다면 필요하다
- UI 컴포넌트 구성(Base UI/shadcn은 첫 화면을 만들 때 설정한다)
- 응답 표시를 어디에 둘지(기도제목, 이어진 기도, 별도 기록)
- 노트 제목을 둘지, 기도한 시각을 사용자가 바꿀 수 있는지
- 동기화를 끄거나 로그아웃할 때 서버와 기기의 데이터 처리
- 커뮤니티 가입 방식(초대 링크 등)
- ID 표기: 명세의 `format: uuid`는 대문자도 받는데, 노트 저장이 ID를 JS 문자열로 비교해서 대문자 ID를 보내면 409가 난다(웹은 소문자라 지금은 드러나지 않는다). 서버가 소문자로 정규화할지, 명세에서 소문자만 받을지 정한다. 2026-10-24 설계 리뷰에서 발견
- 태그 이름의 대소문자 판정: domain의 `toLowerCase()`와 DB의 `lower()`(DB 로케일을 따른다)가 같다는 전제를 문서에 적을지, domain 함수로 만든 정규화 키 컬럼에 유일 인덱스를 걸지(스키마 변경) 정한다. 오프라인 앱이 직접 판정할 때 중요해진다. 2026-10-24 설계 리뷰에서 발견
- 운영 환경(실제 사용자를 받을 때). 미리보기는 ADR-0008
- 카카오에서 받을 동의 항목(이메일은 사업자 인증이 필요하다)

## 타협

구현 중 설계와 어긋나 타협한 지점. 이 꼴로 적는다: `- [타협] YYYY-MM-DD 무엇을 어떻게 타협했나 (관련: [설계 절](../ARCHITECTURE.md#앵커))`
같은 설계 절에 쌓이면 `design-harness check`가 재설계를 검토하라고 알린다. 해결되면 지운다.

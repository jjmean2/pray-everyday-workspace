# ADR-0005: 소셜 로그인을 Arctic과 직접 만든 세션으로 구현

- **상태**: Accepted
- **날짜**: 2026-10-18
- **대체하는 것**: 없음
- **관련**: 계정, 계정과 인증, API 계약, 불변식

## 요약

로그인은 외부 인증 서비스 없이 우리 서버와 DB로 구현한다. OAuth 흐름은 Arctic(OAuth 2.0 클라이언트 라이브러리)으로 처리하고, 사용자, 로그인 수단, 세션은 직접 만든다. 인증 엔드포인트도 OpenAPI 명세에 먼저 정의한다. 처음에는 카카오와 구글로 시작하고, 이메일 가입은 미룬다. 로그인 수단을 이메일로 자동 연결하지 않는다.

## 맥락

사용자는 교회 소그룹이 중심이라 카카오 로그인이 사실상 필수다. 인증 서비스 대신 직접 구현하기로 했다. 그 안에서 인증 전체를 맡는 Better Auth와, OAuth 흐름만 맡는 Arctic을 비교했다(결정 시점 Better Auth 1.7, Arctic 3.7. 둘 다 카카오, 네이버, 애플, 구글을 지원한다).
API 계약은 OpenAPI 명세가 원본이고(ADR-0003), 나중의 네이티브 앱도 같은 명세를 쓴다. 서버는 NestJS 12(ESM)다.

## 결정

- **OAuth 흐름**: Arctic으로 인가 URL 생성, PKCE, 토큰 교환을 한다. state와 code verifier는 짧게 사는 쿠키에 둔다
- **사용자와 로그인 수단**: 사용자 한 명은 로그인 수단(제공자, 제공자의 사용자 ID) 여러 개를 가질 수 있다. 이메일로 자동 연결하지 않는다. 카카오는 사업자 인증을 받은 앱만 이메일을 받을 수 있어 이메일이 믿을 만한 기준이 아니고, 자동 연결은 계정 탈취에 쓰일 수 있다. 다른 수단은 로그인한 상태에서 사용자가 직접 연결한다
- **세션**: 서버 DB에 둔다. 세션 토큰은 무작위로 만들어 쿠키(HttpOnly, Secure, SameSite=Lax)로 주고, DB에는 해시만 저장한다. 나중의 네이티브 앱은 같은 세션 테이블에서 토큰을 발급받는다
- **API 계약**: 로그인 시작, 콜백, 로그아웃, 현재 사용자 조회 엔드포인트를 OpenAPI 명세에 먼저 정의한다
- **제공자**: 카카오와 구글로 시작한다. 애플은 iOS 앱을 만들 때 더한다(다른 소셜 로그인을 제공하는 iOS 앱에는 사실상 필요하다). 네이버는 선택이다. 이메일 가입은 미룬다
- **ID**: 사용자와 세션은 서버가 만드는 레코드라 서버가 ID를 만든다. 클라이언트 생성 ID는 동기화를 위해 클라이언트가 만드는 레코드에 적용한다

## 검토한 대안

- **Better Auth**: 사용자, 세션, 계정 연결, 이메일 로그인, 요청 제한까지 갖춰 직접 짤 보안 코드가 적다. 하지만 엔드포인트를 라이브러리가 정해 "모든 API는 OpenAPI 명세에 있다"는 원칙에 예외가 생기고, NestJS 연동이 앱 전체의 body parser를 끄도록 요구하며, NestJS 12(ESM)에서 확인된 사례가 없었다. 네이티브 ID 토큰 로그인도 구글, 애플, 페이스북만 지원한다
- **외부 인증 서비스 (Clerk, Supabase Auth 등)**: 가장 빠르지만 직접 구현하기로 했다. 카카오 지원과 사용자 데이터의 위치도 서비스에 따라 제약이 생긴다
- **Passport (NestJS 전략)**: NestJS에서 오래 쓰인 방식이지만 제공자별 전략 패키지의 관리 상태가 고르지 않다. OAuth 흐름은 Arctic으로 충분하다
- **이메일로 계정 자동 연결**: 사용자는 편하지만, 이메일 검증이 제공자마다 다르고 계정 탈취 경로가 된다

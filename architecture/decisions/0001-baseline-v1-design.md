# ADR-0001: 첫 설계 기준선

- **상태**: Accepted
- **날짜**: 2026-10-17
- **관련 요구사항**: R-001 ~ R-027
- **대체하는 것**: 없음
- **제안 계기**: 사전 설계

## 요약

"쌓이는 기도"의 첫 설계를 기준선 하나로 묶는다. 핵심은 리더가 소그룹 기도제목을 모아 공유하는 흐름이고, 그 입력이 되는 개인 기록은 메모 앱만큼 편해야 한다.
개인 기록은 **노트와 기도제목**만 기본 단위로 두고 정리를 강제하지 않는다. 공유는 노트의 **스냅샷인 나눔**으로 한다. 개인 영역은 로컬 우선, 커뮤니티 영역은 서버 중심으로 나눈다.

## 맥락

브레인스토밍에는 개인 기도 노트와 소그룹 공유가 함께 있었다. 논의 끝에 소그룹 공유가 서비스의 존재 이유이고, 개인 기록의 편의가 그 전제 조건이라고 정했다.
같은 기도제목을 오래 기도하는 일이 많지만, 쓰는 순간에 기도제목(주제)을 만들고 고르게 하면 기록이 무거워지고, 묶인 것과 안 묶인 것이 섞여 오히려 이해하기 어려워진다.
웹을 먼저 만들고 혼자 개발한다. 나중에 앱에서 가입 없이 쓰는 로컬 전용 모드를 제공한다.

## 결정

- **D-01 기록 중심 모델**: 노트(기도한 시각, 자유 글 메모, 기도제목 목록)와 기도제목(제목과 상세 중 하나 이상)이 기본 단위다. 주제 컨테이너는 두지 않는다. 같은 기도의 묶음(이어진 기도)은 "오늘도 기도"와 연결로 쓰는 중에 저절로 생기고, 정리는 나중에 쉽게 한다
- **D-02 기도제목의 경계는 사용자가 정한다**: 한 행이 기도제목 하나이고 Enter로 새 기도제목을 만든다. 서식에서 기도제목을 추론하지 않는다
- **D-03 나눔은 노트의 스냅샷**: 서버의 별도 엔티티이고 원본에는 연결만 한다. 공개 범위는 나눔에 붙는다. 나눔의 주인은 작성자다
- **D-04 개인 영역과 커뮤니티 영역의 분리**: 개인 영역은 로컬 우선, 커뮤니티 영역은 서버 중심이다. 두 영역은 나눔으로만 연결된다
- **D-05 원본 규칙**: 앱에서 가입 전에는 기기 DB가 원본이다. 동기화를 켜면 서버가 원본이고 기기 DB는 복제본이다. 웹은 로그인과 동기화가 필수다
- **D-06 동기화할 수 있는 스키마**: 클라이언트에서 만든 ID, 레코드별 버전과 수정 시각, 삭제 표시(tombstone), 서버의 변경 순서를 웹 단계부터 갖춘다
- **D-07 스택**: TypeScript 모노리포. 웹은 React, Tailwind CSS, Base UI(shadcn), 서버는 NestJS, 앱의 기기 DB는 SQLite

## 검토한 대안

- **주제(기도제목) 컨테이너를 필수로**: 이어지는 기도를 잘 표현하지만, 매일 쓰는 순간 정리를 요구해 기록이 무거워지고 파편화된다
- **자유 마크다운에서 기도제목 추론**: 쓰기는 가장 자유롭지만, bullet 하나가 기도제목 하나라는 보장이 없어 이어짐, 나눔, 응답이 흔들린다
- **개인 기도제목을 공개 범위만 바꿔 그대로 공유(참조)**: 원본 변경이 바로 반영되지만, 개인 노트가 서버와 다른 사람에게 노출되고 리더의 모음 글이 예고 없이 바뀐다
- **서버 원본에 오프라인 캐시만 붙이기**: 단순하지만 가입 없는 로컬 전용 모드를 지원할 수 없다
- **완전한 로컬 우선(CRDT, 서버는 중계)**: 오프라인에 가장 강하지만 커뮤니티의 권한과 공유가 어렵고, 개인 노트에는 동시 편집이 드물어 비용에 비해 이득이 작다
- **웹에서도 로그인 없는 로컬 전용**: 진입 장벽은 낮지만 브라우저가 저장소를 지울 수 있어 기록을 잃을 위험이 있다

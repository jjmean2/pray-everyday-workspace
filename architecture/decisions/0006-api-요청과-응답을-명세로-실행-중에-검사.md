# ADR-0006: API 요청과 응답을 명세로 실행 중에 검사

- **상태**: Accepted
- **날짜**: 2026-10-18
- **대체하는 것**: 없음
- **관련**: API 계약, 계정과 인증

## 요약

서버는 `openapi.yaml`을 실행 중에 읽어 모든 요청을 검사하고, 개발과 테스트에서는 응답도 검사한다(express-openapi-validator). 엔드포인트마다 검증 코드를 쓰지 않는다. 명세에 없는 경로는 404이고, 검사 오류는 Problem Details로 돌려준다.

## 맥락

명세에서 생성한 TypeScript 타입은 실행할 때 사라지므로, 들어오는 요청이 명세에 맞는지는 따로 검사해야 한다. 첫 API(개발용 로그인)는 명세의 규칙을 컨트롤러에서 손으로 다시 적어 검사했고, 설계 리뷰에서 그 코드가 명세에 없는 규칙(공백 다듬기)을 더한 것이 드러났다. 같은 규칙이 명세와 코드 두 곳에 있으면 어긋나고, 에이전트가 엔드포인트마다 검사 코드를 쓰면 빠뜨리거나 다르게 쓰기 쉽다.
서버는 NestJS 12(Express 5)이고, API 계약은 명세 우선이다(ADR-0003).

## 결정

- express-openapi-validator(결정 시점 5.6)를 앱 설정에 붙여 `@pray/api-contract`의 `openapi.yaml`로 모든 요청의 본문, 파라미터, Content-Type을 검사한다. 컨트롤러는 검사를 통과한 요청만 받고 명세의 타입을 그대로 쓴다
- 응답 검사는 서버 버그를 잡는 장치라 `NODE_ENV=production`이 아닐 때만 켠다. 명세와 다른 응답은 500으로 드러나고 내부 정보는 담지 않는다
- 인증은 검사기가 아니라 세션 가드 한 곳에서 판단한다(검사기의 보안 검사는 끈다)
- 검사기는 파싱된 본문을 보므로 그 앞에 JSON 파서를 둔다(Nest의 본문 파서는 사용자 미들웨어보다 늦게 붙는다)
- 명세의 모든 엔드포인트는 따로 적지 않은 오류를 `default` 응답(Problem Details)으로 선언한다. 응답 검사가 404 같은 오류 응답을 명세 위반으로 보지 않게 하고, "모든 오류는 Problem Details"를 명세에도 드러낸다

## 검토한 대안

- **명세에서 Zod 스키마를 생성(@hey-api/openapi-ts)해 NestJS 12의 `StandardSchemaValidationPipe`로 검사**: NestJS다운 방식이고 생성한 스키마를 웹 폼에서도 쓸 수 있다. 하지만 엔드포인트마다 스키마를 붙여야 해 빠뜨릴 수 있고, 생성기가 0.x라 깨지는 변경이 잦으며, 생성 과정에서 JSON Schema와 의미가 달라질 수 있다(길이 세는 방식 등)
- **Ajv로 명세의 스키마를 직접 검사하는 파이프를 직접 작성**: 표준 그대로 검사하고 의존성이 가장 적다. 하지만 연결 코드를 직접 유지해야 하고 엔드포인트마다 붙여야 한다. 검사기가 맞지 않으면 쓰려던 대비책이었다
- **손으로 검사 코드나 DTO(class-validator)를 쓰기**: 규칙이 명세와 코드 두 곳에 생겨 명세 우선 원칙과 맞지 않는다

검사기는 Express 단계의 미들웨어라 NestJS 바깥에서 동작하고 업데이트가 잦지 않다(결정 시점 마지막 릴리스 2026-01). NestJS 12와 Express 5에서 동작하는 것은 시험 구현과 e2e 테스트로 확인했다.

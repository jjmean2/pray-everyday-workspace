# ADR-0007: 개인 기록의 저장 방식: 레코드 단위 충돌 처리, 분수 인덱스, 태그 배열

- **상태**: Accepted
- **날짜**: 2026-10-23
- **대체하는 것**: 없음 (ADR-0001의 "필드 단위로 마지막 수정이 이긴다"를 레코드 단위로 바꾼다)
- **관련**: 개인 기록 모델, 데이터 원본과 동기화, API 계약

## 요약

노트, 기도제목, 태그를 각각 동기화 장치를 가진 레코드로 저장하고, 충돌은 레코드 단위로 마지막 수정이 이긴다. 노트 안의 기도제목 순서는 분수 인덱스로, 태그는 노트와 기도제목 레코드 안의 태그 ID 목록으로 둔다. 웹은 노트 하나를 통째로 저장하는 API를 쓴다.

## 맥락

노트 쓰기(첫 개인 기록 기능)를 구현하면서 동기화 장치(클라이언트 생성 ID, 버전, 수정 시각, 삭제 표시, 변경 순번)가 처음 테이블에 들어갔다. 이전 결정(ADR-0001)은 충돌을 "필드 단위"로 처리한다고 했는데, 이를 지키려면 필드마다 수정 시각을 따로 저장해야 한다. 기도제목은 이미 노트와 별도의 레코드라 레코드 단위로도 충분히 잘게 나뉜다.
웹은 항상 온라인이고, 에디터는 쓰는 동안 노트를 자동으로 저장한다. 나중의 앱은 오프라인에서 쓰고 변경을 묶어 동기화한다.

## 결정

- **충돌**: 레코드 단위(노트, 기도제목, 태그 각각)로 마지막 수정이 이긴다. 레코드마다 버전(서버가 올림), 수정 시각, 삭제 표시, 서버 전역 변경 순번을 둔다
- **순서**: 노트 안의 기도제목 순서는 분수 인덱스(문자열 정렬 키)다. 클라이언트가 두 키 사이의 새 키를 만들고, 서버는 키를 정렬에만 쓴다
- **태그 연결**: 노트와 기도제목에 태그 ID 목록(PostgreSQL 배열)을 둔다. 연결은 그 레코드의 수정이고, 삭제 표시된 태그는 읽을 때 걸러 낸다
- **이어진 기도**: 기도제목의 이어진 기도 ID 칸만 미리 둔다
- **웹 API**: `PUT /notes/{id}`로 노트를 기도제목과 함께 통째로 저장한다. 클라이언트 생성 ID라 멱등이고, 목록에서 빠진 기도제목은 삭제 표시한다. 다른 사람의 레코드는 404로 감춘다
- **검사와 인증의 순서**: 명세 검사가 인증보다 먼저다(형식 오류는 401보다 400이 먼저). 명세의 경로에 없는 메서드는 405다

## 검토한 대안

- **필드 단위 충돌 처리**: 가장 잘게 병합하지만 필드마다 시각을 저장해야 해 무겁다. 개인 노트는 동시 편집이 드물다
- **정수 순번**: 단순하지만 끼우거나 옮기면 뒤의 행이 모두 바뀌어 동기화할 변경이 늘어난다
- **태그 연결 테이블**: 외래 키를 걸 수 있지만 연결 행마다 동기화 장치가 필요해 동기화 단위가 늘어난다
- **기도제목마다 따로 저장하는 API**: 레코드와 1:1로 맞지만 에디터가 요청을 많이 보내고, 순서와 삭제를 맞추기 어렵다. 앱의 묶음 동기화 API는 나중에 따로 둔다

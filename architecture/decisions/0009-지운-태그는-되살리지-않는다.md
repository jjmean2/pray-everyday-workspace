# ADR-0009: 지운 태그는 되살리지 않는다

- **상태**: Accepted
- **날짜**: 2026-10-24
- **대체하는 것**: 없음 (ADR-0007의 "레코드 단위로 마지막 수정이 이긴다"에 태그의 삭제만 예외를 둔다)
- **관련**: 개인 기록 모델, 데이터 원본과 동기화

## 요약

삭제 표시된 태그를 같은 ID로 다시 저장하면 되살리지 않고 409로 거절한다. 태그에 한해서는 삭제가 그 뒤의 수정보다 이긴다. 지운 태그의 이름은 새 태그(새 ID)에 쓸 수 있다.

## 맥락

ADR-0007은 노트, 기도제목, 태그 모두 레코드 단위로 마지막 수정이 이기고, 삭제 표시된 레코드도 같은 ID로 다시 저장하면 되살아난다고 정했다. 태그 연결은 노트와 기도제목 안의 태그 ID 목록이고, 삭제 표시된 태그는 읽을 때 걸러 낸다. 그래서 태그를 지운 뒤 다시 저장된 노트와 기도제목에서는 그 태그가 이미 빠져 있다. 이때 태그를 되살리면, 그사이 다시 저장되지 않은 레코드에서만 태그가 돌아와 레코드마다 결과가 달라진다. 사용자가 예상할 수 있는 결과가 아니다.

## 결정

- 삭제 표시된 태그를 같은 ID로 저장하면 409다. 서버는 태그 행을 잠가 저장과 삭제를 차례대로 처리하므로, 읽은 뒤에 지워진 경우도 409다
- 지운 태그의 이름은 겹침 검사에서 빠지므로 새 태그에 다시 쓸 수 있다
- 클라이언트(나중의 오프라인 앱)가 동기화하다 이 409를 받으면 그 태그를 지워진 것으로 처리하고 자기 쪽 변경(이름 바꾸기)은 버린다. 사용자가 다시 원하면 새 태그로 만든다
- 노트와 기도제목은 ADR-0007대로 되살아난다

## 검토한 대안

- **ADR-0007대로 되살리기**: 규칙이 하나로 통일된다 — 위의 이유로 레코드마다 태그가 돌아오기도 하고 안 돌아오기도 한다
- **되살릴 때 지웠던 연결도 복원**: 결과는 일관되지만 지운 시점의 연결을 따로 보관해야 하고, 그사이 사용자가 바꾼 노트와 충돌한다

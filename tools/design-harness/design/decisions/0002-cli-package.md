# ADR-0002: CLI 중심 패키지로 분리

- **상태**: Proposed
- **날짜**: 2026-10-17
- **관련 요구사항**: R-008, R-012
- **대체하는 것**: D-08
- **제안 계기**: 요구사항 변경

## 맥락

R-008(다른 프로젝트에 설치)과 R-012(기계적 문서 조작)는 D-08의 "이 저장소 하나에서만 쓴다"는 가정을 깬다.
지금은 검사 스크립트가 각 프로젝트에 복사돼 있어야 하고, ADR 번호 매기기, 상태 변경, archive 이동, 링크 갱신은 에이전트가 손으로 한다.
손으로 하는 조작은 에이전트마다 결과가 다르고, 검사기가 잡아내기 전까지 규약 위반이 생긴다.

## 결정

design-harness를 **CLI가 중심인 패키지**로 별도 저장소에 분리한다.

### 패키지 구성

| 구성 요소 | 내용 | 프로젝트에 들어가는 방식 |
|---|---|---|
| CLI | 명령 진입점과 로직 | 들어가지 않는다. 고정한 버전으로 실행한다 |
| 자산(assets) | 규약 문서, 리뷰 체크리스트, 템플릿, 관리 블록 원문, skill 원본, 어댑터 파일 | `init`과 `update`가 도구 소유 파일로 복사한다 |
| 선택적 plugin | Claude Code plugin(도입용 skill 포함) | 개인이 설치. 필수 아님 (ADR-0004) |

에이전트는 파일을 읽어야 규칙을 알기 때문에 **문서와 skill은 저장소에 복사하고, 코드는 복사하지 않는다.**

### 명령 체계

| 명령 | 하는 일 |
|---|---|
| `check` | 정합성 검사 (지금의 `check-design.py`) |
| `context <경로>` | 스코프 체인, 결정 대기, 미분석 요구사항, 열린 마찰 출력 |
| `adr new "<제목>"` | 템플릿으로 다음 번호의 `Proposed` ADR을 만들고 결정 대기에 링크 |
| `adr accept <ID> [--supersedes <ID>]` | 상태를 `Accepted`로 바꾸고 대체된 ADR을 `Superseded`로 바꿔 archive로 이동. 남은 수동 단계(결정 표 갱신, 레거시 등록)를 목록으로 출력 |
| `adr reject <ID>` | `Rejected`로 바꾸고 archive로 이동, 결정 대기에서 제거 |
| `req retire <ID> (--reason <이유> \| --replaced-by <ID>)` | 요구사항을 archive로 이동 |
| `scope new <경로>` | 스코프 뼈대를 만들고 루트 목록에 등록 |
| `squash [--apply]` | 근거에서 빠진 `Accepted` ADR을 archive로 이동. 기본은 후보만 출력 |
| `init`, `update`, `migrate`, `eject` | 생애주기 (ADR-0003, ADR-0004) |

- 스코프는 `--scope <경로>`로 지정하고, 생략하면 현재 디렉터리에서 가장 가까운 스코프로 정한다
- 모든 명령에 `--json`을 둬서 에이전트가 출력을 기계적으로 읽게 한다
- 파일을 바꾸는 명령은 `--dry-run`을 지원한다. 되돌리기는 git에 맡긴다
- **CLI는 판단하지 않는다.** 결정 표의 내용, 영향 분석, 아키텍처 서술은 쓰지 않는다. 판단이 필요한 단계는 "남은 작업" 목록으로 출력한다

### 내부 구조

| 모듈 | 책임 | 의존 |
|---|---|---|
| `cli` | 인자 해석, 출력 형식(텍스트, JSON) | `ops`, `rules`, `installer` |
| `model` | 설계 문서를 읽고 쓰는 유일한 모듈. 표, 상태 줄, 관리 블록의 형식을 안다 | 없음 |
| `rules` | 검사 규칙. 모델을 받아 오류, 경고, 안내를 낸다 | `model` |
| `ops` | 문서 조작 명령. 모든 쓰기는 `model`을 거친다 | `model` |
| `installer` | `init`, `update`, `eject`. 자산을 복사하고 manifest를 관리한다 | `model`, `assets` |
| `migrations` | 규약 버전 간 변환 | `model` |
| `assets` | 규약 버전별 자산 원본 | 없음 |

문서 형식에 대한 지식을 `model` 하나에 모아 두면, 형식이 바뀔 때 고칠 곳과 마이그레이션 대상이 한곳에 모인다.

### 언어와 배포

- **언어**: Python 3.11 이상, 표준 라이브러리만 사용. 지금 구현을 그대로 옮길 수 있다
- **배포**: PyPI. `uvx design-harness@<버전>`으로 설치 없이 실행하거나 `pipx`로 설치한다
- **버전 고정**: 프로젝트는 `harness.toml`에 도구 버전을 적고, 관리 블록 안의 hook이 그 버전으로 실행한다 (ADR-0003)

## 검토한 대안

- **스크립트를 계속 복사해서 배포 (Copier 템플릿 등)**: 구조가 단순하지만 코드가 프로젝트마다 복제되고, 업데이트할 때 병합 충돌이 코드에서도 생긴다
- **Claude Code plugin만으로 배포**: 설치가 쉽지만 다른 에이전트와 사람, CI가 검사를 쓸 수 없어 D-06과 충돌한다
- **Go 단일 바이너리**: Python이 없는 환경에서도 돌지만 지금 구현을 다시 써야 하고, 대상 사용자 환경에는 대개 Python과 uv가 있다
- **npm 패키지**: Node 프로젝트에는 자연스럽지만 그 밖의 프로젝트에 Node 의존이 생긴다

## ARCHITECTURE.md 반영안

- **결정**: design-harness는 별도 저장소의 CLI 패키지다. 코드는 프로젝트 밖에서 고정 버전으로 실행하고, 문서와 skill 같은 자산만 도구 소유 파일로 프로젝트에 복사한다. CLI는 결정적인 검증과 파일 조작만 한다
- **전제한 가정**: 대상 환경에서 Python 3.11 이상과 `uvx` 또는 `pipx`를 쓸 수 있다
- **수용하지 못하는 것**: Python을 쓸 수 없는 환경, 도구 없이 오프라인으로 처음 설치하는 경우
- **재검토 트리거**: Python 없는 환경에서 쓰려는 요구가 생길 때, 명령이 판단을 해야 하는 요구가 생길 때

모듈과 경계 표를 위 "내부 구조"로 바꾸고, 구현 위치를 새 저장소로 고친다.

## 정리 대상

- `.githooks/pre-commit`의 직접 실행 줄: 고정 버전의 CLI 실행으로 대체
- `AGENTS.md`와 규약 문서 안의 `python3 design/harness/bin/check-design.py` 표기: CLI 명령으로 대체

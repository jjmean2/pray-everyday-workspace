# ADR-0003: 규약 버전, 업데이트, 마이그레이션

- **상태**: Proposed
- **날짜**: 2026-10-17
- **관련 요구사항**: R-010, R-011
- **대체하는 것**: 없음 (D-05를 구체화한다)
- **제안 계기**: 요구사항 변경

## 맥락

하네스는 프로젝트 저장소에 상태(설계 문서)를 남긴다. 그래서 일반적인 skill이나 plugin과 달리 업데이트가 "교체"로 끝나지 않는다.

- 도구 소유 파일은 교체하면 되지만, 프로젝트가 몰래 고쳤다면 그 변경이 사라진다
- 새 버전에서 없어진 도구 소유 파일은 지워야 하는데, 무엇을 설치했는지 기록이 없으면 알 수 없다
- 규약 형식(표의 열, 상태 값, 폴더 구조)이 바뀌면 프로젝트 소유 문서도 바뀌어야 한다

D-05는 버전이 같은지만 검사하고, 다를 때 무엇을 할지는 정하지 않았다.

## 결정

### 버전 두 가지

| 버전 | 형식 | 의미 | 위치 |
|---|---|---|---|
| **규약 버전** | 정수 (`1`, `2`, …) | 프로젝트 소유 문서의 형식과 관리 블록의 의미 | `harness.toml`의 `harness.version`, 관리 블록의 `begin vN` |
| **도구 버전** | semver | CLI와 자산의 릴리스 | `harness.toml`의 `harness.tool` |

- 도구의 major 버전은 규약 버전이 바뀔 때만 올린다
- 도구는 자기가 지원하는 규약 버전 하나를 알고, 직전 버전들에서 그 버전으로 가는 마이그레이션을 가진다

```toml
[harness]
version = 1          # 규약 버전
tool = "1.2.0"       # 이 프로젝트가 고정한 도구 버전
agents = ["claude"]  # 설치한 어댑터 (ADR-0004)
```

### Manifest

도구 소유 파일 목록과 해시를 `design/harness/manifest.json`에 기록한다. 이 파일도 도구가 소유한다.

```json
{ "tool": "1.2.0", "convention": 1,
  "files": { "design/harness/README.md": "sha256:…", ".claude/agents/design-reviewer.md": "sha256:…" } }
```

### `update` (같은 규약 버전 안에서)

1. manifest의 각 파일 해시를 실제 파일과 비교한다. 다르면 **프로젝트가 고친 것**으로 보고 멈춘 뒤 목록을 보여 준다. `--force`가 있을 때만 덮어쓴다
2. 새 자산을 쓰고, 이전 manifest에 있었지만 새 버전에 없는 파일은 지운다
3. 공동 소유 파일의 관리 블록을 새 원문으로 교체한다. 블록 밖은 건드리지 않는다
4. manifest와 `harness.tool`을 갱신한다
5. 프로젝트 소유 파일은 건드리지 않는다

### `migrate` (규약 버전이 바뀔 때)

- `harness.version`이 도구의 규약 버전보다 낮으면 `check`와 `update`가 실패하고 `migrate`를 안내한다. 더 높으면 도구가 오래됐다고 안내한다
- `migrate`는 버전 단계마다(`N → N+1`) 결정적인 변환을 차례로 실행한 뒤 `update`를 실행하고 `harness.version`을 올린다
- 변환은 `model` 모듈을 거치고, 여러 번 실행해도 결과가 같아야 한다
- **판단이 필요한 변환은 추측하지 않는다.** 예를 들어 새 필수 칸의 값이 그렇다. 칸은 `미분석` 같은 표시로 두고 "남은 작업" 목록을 출력한다
- 결과는 커밋하지 않은 변경으로 남겨 사람이 diff를 리뷰하고 커밋한다

## 검토한 대안

- **Copier의 3-way 병합으로 업데이트**: 도구 소유 파일까지 병합하게 되어 "직접 고치지 않는다"는 소유권 규칙이 흐려지고, 관리 블록 단위 교체와 맞지 않는다
- **manifest 없이 덮어쓰기**: 단순하지만 프로젝트가 고친 내용을 조용히 잃고, 없어진 파일이 남는다
- **규약 버전 없이 도구 버전만 사용**: 문서 형식이 바뀌었는지 도구 릴리스마다 따져야 해서 마이그레이션 필요 여부가 불분명해진다

## ARCHITECTURE.md 반영안

- **결정**: 규약 버전(정수)과 도구 버전(semver)을 나눈다. 도구 소유 파일은 manifest로 추적해 수정 감지와 삭제를 하고, `update`는 도구 소유 파일과 관리 블록만, `migrate`는 결정적인 단계별 변환으로 프로젝트 문서를 바꾸며 판단이 필요한 부분은 남은 작업으로 넘긴다
- **전제한 가정**: 규약 변경을 결정적인 변환과 사람의 판단으로 나눌 수 있다. 프로젝트는 변경을 git으로 리뷰한다
- **수용하지 못하는 것**: 규약 버전을 건너뛰는 부분 채택, 도구 소유 파일의 프로젝트별 수정 유지
- **재검토 트리거**: `--force` 사용이 잦아질 때(프로젝트가 도구 소유 파일을 고칠 이유가 있다는 신호), 결정적으로 변환할 수 없는 규약 변경이 생길 때

불변식에 추가: "도구 소유 파일은 manifest에 있는 것뿐이고, manifest의 해시와 일치한다"

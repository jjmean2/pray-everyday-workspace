# ADR-0004: 도입 경로와 에이전트 어댑터

- **상태**: Proposed
- **날짜**: 2026-10-17
- **관련 요구사항**: R-008, R-009, R-013, R-014
- **대체하는 것**: 없음
- **제안 계기**: 요구사항 변경

## 맥락

하네스 도입은 skill이나 plugin 설치와 다르다. 저장소에 문서를 만들고 커밋해야 하고, `AGENTS.md`처럼 하네스가 통째로 소유할 수 없는 파일을 건드려야 한다.
새 프로젝트와 기존 프로젝트는 출발점이 다르다. 기존 프로젝트에는 코드, 지시 파일, hook 체계, 기존 ADR이 이미 있을 수 있다.
에이전트마다 skill과 서브에이전트를 두는 위치와 형식도 다르다.

## 결정

### `init`: 도입의 기계적인 부분

`harness.toml`이 없는 저장소에서 실행한다. 만드는 것:

| 대상 | 처리 |
|---|---|
| `design/` 루트 스코프 | ARCHITECTURE, REQUIREMENTS, friction-log, `decisions/`, `archive/` 뼈대 |
| `design/harness.toml` | 규약 버전, 도구 버전, 어댑터 목록 |
| `design/harness/` | 자산(규약 문서, 체크리스트, 템플릿, skill 원본)과 manifest |
| `AGENTS.md` | 없으면 만들고, 있으면 끝에 관리 블록을 추가한다. 기존 내용은 건드리지 않는다 |
| `CLAUDE.md` (claude 어댑터) | 없으면 `@AGENTS.md` 한 줄로 만든다. 있으면 `@AGENTS.md`를 담은 관리 블록을 추가한다. Claude Code는 기본 설정에서 `CLAUDE.md`가 있으면 `AGENTS.md`를 읽지 않기 때문이다 |
| 커밋 전 검사 | `.pre-commit-config.yaml`이 있으면 관리 블록으로 hook 항목을 추가한다. 없으면 `.githooks/pre-commit`을 만들고 `core.hooksPath` 설정을 안내한다. husky처럼 모르는 hook 체계가 있으면 건드리지 않고 추가할 명령만 안내한다 |
| 어댑터 | `--agents`로 고른 도구별로 설치 (아래) |

`init`이 끝나면 만든 파일과 남은 작업을 출력한다. 커밋은 사람이 한다.

### 기존 프로젝트: `init` + 도입 skill

기존 프로젝트는 `init` 뒤에 **도입(adopt) skill**로 내용을 채운다. 내용 작성은 판단이라 CLI가 하지 않는다.

1. 에이전트가 코드를 분석해 **실제 현재 구조**를 ARCHITECTURE.md 초안으로 쓴다. 바람직한 구조가 아니다
2. 현재 결정들을 `ADR-0001: 도입 시점 기준선` 하나로 등록하고 D-ID를 붙인다. 과거 결정을 소급해서 지어내지 않는다
3. 이미 알려진 나쁜 패턴은 "이행 중인 레거시"에 넣는다
4. 코드, 문서, 이슈에서 요구사항을 역추출해 `구현됨`으로 등록한다
5. 기존 ADR 폴더가 있으면 그대로 두고, 가져올지 archive로 옮길지는 사람이 정하도록 제안한다
6. 처음에는 루트 스코프 하나로 시작하고, 손대는 영역이 생길 때 스코프를 추가한다

사람이 초안을 리뷰하고 커밋한다.

### 어댑터

규약을 전달하는 원본은 도구 중립 형식으로 하나만 두고, 어댑터가 각 도구의 위치와 형식으로 복사한다.

| 원본 (자산) | 형식 |
|---|---|
| skill: 영향 분석, 설계 변경, 설계 리뷰, 정리, 스코프 관리, 도입 | `SKILL.md` (Agent Skills 형식) |
| 리뷰 체크리스트 | Markdown |

| 어댑터 | 설치하는 것 |
|---|---|
| `generic` | 없음. `AGENTS.md` 관리 블록과 자산 문서만으로 동작 (항상 포함) |
| `claude` | `.claude/skills/`에 skill, `.claude/agents/design-reviewer.md`, `CLAUDE.md` 처리 |
| 그 밖의 도구 | 각 도구가 skill과 지시 파일을 읽는 위치로 복사. 도구별 경로는 어댑터 정의에 두고, 공식 문서로 확인한 도구만 추가한다 |

- 설치한 어댑터는 `harness.toml`의 `agents`에 기록하고, `update`가 같은 목록으로 다시 설치한다
- **항상 적용할 규칙은 skill에 두지 않는다.** skill은 필요할 때만 불러와진다. 상시 규칙은 `AGENTS.md` 관리 블록에 두고, skill에는 절차만 둔다

### 선택적 plugin

Claude Code plugin을 개인용 진입로로 제공한다. 아직 도입하지 않은 저장소에서 도입 skill을 실행할 수 있게 하고, 그 skill은 내부에서 `init`을 실행한다. 도입한 뒤에는 프로젝트에 설치된 어댑터가 기준이다.

### `eject`: 제거

- manifest의 도구 소유 파일, 공동 소유 파일의 관리 블록, 설치한 어댑터, `harness.toml`을 지운다
- **프로젝트 소유 설계 문서는 남긴다.** 규약 없이도 읽을 수 있는 평범한 Markdown이다

## 검토한 대안

- **plugin 설치만으로 도입**: 프로젝트에 문서와 규칙이 남지 않아 다른 에이전트, 팀원, CI가 규약을 모른다
- **skill을 사용자 수준에만 설치**: 프로젝트마다 규약 버전이 달라도 같은 skill을 쓰게 되어 버전이 어긋난다
- **`AGENTS.md`를 하네스가 통째로 생성하고 소유**: 프로젝트 고유 규칙을 둘 곳이 없어지고, 기존 프로젝트에 도입할 수 없다
- **CLI가 기존 코드를 분석해 아키텍처를 자동 생성**: 판단을 CLI에 넣는 것이라 D-07과 "CLI는 판단하지 않는다"는 원칙에 어긋나고, 결과를 믿기 어렵다

## ARCHITECTURE.md 반영안

- **결정**: 도입은 `init`(기계적 생성)과 도입 skill(내용 작성)으로 나눈다. 공동 소유 파일에는 관리 블록만 추가한다. 어댑터는 도구 중립 원본을 각 도구 위치에 복사하고, 상시 규칙은 skill이 아닌 `AGENTS.md`에 둔다. `eject`는 설계 문서를 남긴다
- **전제한 가정**: 지원하는 에이전트는 `AGENTS.md`나 import를 읽고, skill은 Agent Skills 형식을 읽는다
- **수용하지 못하는 것**: 관리 블록을 넣을 수 없는 지시 파일 형식, 프로젝트 저장소에 파일을 둘 수 없는 환경
- **재검토 트리거**: 어댑터마다 skill 내용을 따로 고쳐야 하는 일이 생길 때, 도입 skill의 초안을 사람이 대부분 다시 쓰는 일이 반복될 때

## 정리 대상

- `.claude/agents/design-reviewer.md` 수동 배치: `claude` 어댑터 설치로 대체
- `CLAUDE.md`의 수동 `@AGENTS.md`: `claude` 어댑터의 관리 블록으로 대체

# 설계 문서 체계

사람과 Agent가 함께 쓰는 설계 문서의 운영 절차다. 항상 지켜야 하는 핵심 규칙은 [AGENTS.md](../../AGENTS.md)에 있고, 이 문서는 절차의 세부를 다룬다.

## 원칙

1. **현재 상태와 이력을 분리한다.** 구속력은 `ARCHITECTURE.md`와 `REQUIREMENTS.md`에만 있다. 이 둘은 항상 현재 상태로 다시 쓰고 이력을 남기지 않는다.
2. **ADR은 이유의 기록이지 규칙의 출처가 아니다.** ADR이 쌓여도 지켜야 할 규칙은 늘어나지 않는다.
3. **폐기된 것은 바로 치운다.** 대체되거나 기각된 ADR, 폐기된 요구사항은 `archive/`로 옮긴다. archive는 기본적으로 읽지 않는다.
4. **결정은 영향을 받는 가장 낮은 스코프에 둔다.** 그래야 그 부분이 사라질 때 결정도 함께 사라진다.
5. **이력은 git에 있다.** 문서 안에 "예전에는 X였다"를 쓰지 않는다.

## 스코프

스코프는 `design/` 폴더를 가진 디렉터리다. 루트의 `design/`은 시스템 전체 스코프다.

```
design/                      루트 스코프 (시스템 전체)
apps/web/design/             프로젝트 스코프
apps/web/src/sync/design/    하위 시스템 스코프
```

각 스코프의 `design/` 구성:

| 경로 | 구속력 | 내용 |
|---|---|---|
| `ARCHITECTURE.md` | 있음 | 현재 유효한 설계와 결정 |
| `REQUIREMENTS.md` | 있음 | 현재 유효한 요구사항. 하위 시스템 스코프는 생략 가능 |
| `friction-log.md` | 없음 | 아직 해결되지 않은 마찰 |
| `decisions/` | 없음 | ADR. `Proposed`와 `Accepted`만 둔다 |
| `archive/` | 없음 | 대체·기각된 ADR, 폐기·대체된 요구사항. 기본적으로 읽지 않는다 |

### 읽는 순서와 우선순위

어떤 경로에서 작업할 때는 루트부터 그 경로를 포함하는 가장 가까운 스코프까지 `ARCHITECTURE.md`를 차례로 읽는다.
상위 규칙은 하위에도 적용된다. 하위 스코프는 규칙을 더할 수만 있고 뒤집을 수 없다.

### 스코프를 만들 때

- 상위 문서와 독립된 모델, 경계, 결정이 생길 때 만든다
- `ARCHITECTURE.md`가 400줄을 넘으면 분리하라는 신호다
- [templates/](templates/)의 양식으로 만들고, 루트 `ARCHITECTURE.md`의 "스코프 목록"에 등록한다
- 상위 스코프에 있던 결정 중 이 스코프에만 해당하는 것은 옮겨 온다(강등)

### 결정을 옮길 때

- **승격**: 하위 스코프의 결정이 다른 스코프에도 필요해지면 공통 상위 스코프로 올린다
- **강등**: 상위 결정이 사실상 한 스코프에만 영향을 주면 그 스코프로 내린다
- **스코프 삭제**: 코드가 사라지면 그 `design/`도 함께 지우고 루트 목록에서 뺀다. archive로 옮기지 않는다. git에 남아 있다

## ID 규칙

| 종류 | 형식 | 범위 |
|---|---|---|
| 요구사항 | `R-001` | 스코프 안에서 유일, 재사용 금지 |
| 현재 결정 | `D-01` | 스코프 안에서 유일, 재사용 금지 |
| ADR | `ADR-0001`, 파일명 `0001-짧은-제목.md` | 스코프 안에서 유일, 재사용 금지 |

다른 스코프를 참조할 때는 경로를 붙인다. 예: `apps/web:D-03`

`D-ID`는 `ARCHITECTURE.md`의 "현재 유효한 결정" 표에 있는 행이다. 결정이 대체되면 그 행을 지우고 새 `D-ID`를 만든다. 마찰 로그와 요구사항은 `D-ID`를 참조한다.

## 설계 변경 절차

요구사항 변경, 구현 중 발견, 마찰 누적, 요구사항은 그대로인 리팩터링 모두 같은 절차를 따른다.

**ADR이 필요한 경우**: `ARCHITECTURE.md`의 결정, 모델, 상태, 경계, 불변식이 바뀔 때.
그 밖의 변경(모듈 내부 리팩터링, 이름 정리 등)은 커밋 메시지로 충분하다. ADR을 남발하면 그것도 노이즈다.

1. **제안**: [templates/adr.md](templates/adr.md)로 `decisions/NNNN-제목.md`를 `Proposed`로 작성한다. `ARCHITECTURE.md`의 "현재 상태 > 결정 대기"에 링크한다.
2. **결정**: 사람이 결정한다.
   - 기각하면 `Rejected`로 바꾸고 `archive/decisions/`로 옮긴다. 결정 대기에서 뺀다.
3. **문서 갱신**: 승인하면 구현보다 문서를 먼저 고친다.
   - ADR을 `Accepted`로 바꾼다
   - `ARCHITECTURE.md`를 현재 상태로 다시 쓴다. 대체된 `D-ID` 행은 지우고, 새 행을 추가해 근거로 이 ADR을 링크한다. 모델, 경계, 불변식도 고친다
   - ADR의 "정리 대상"을 "이행 중인 레거시" 표에 옮긴다
   - 대체된 ADR은 `Superseded by ADR-NNNN`으로 바꾸고 `archive/decisions/`로 옮긴다
   - 영향을 받는 요구사항의 "관련 결정"을 고친다
4. **구현**
5. **정리**: 레거시 코드와 테스트를 지우고 "이행 중인 레거시"에서 그 행을 지운다. 해결된 마찰 로그 행도 지운다.

## 요구사항 변경

- **문구 수준의 수정**: 제자리에서 고치고 설계 분류를 `미분석`으로 되돌린다
- **의미가 바뀌는 변경**: 새 ID를 만든다. 옛 항목은 [archive/requirements.md](../archive/requirements.md)로 옮기고 처리 칸에 `대체 → R-NNN`을 적는다
- **폐기**: archive로 옮기고 처리 칸에 `폐기`와 이유를 적는다
- **사람이 직접 요구사항을 추가하거나 고칠 때**: 설계 분류를 `미분석`으로 두면 Agent가 다음 작업 전에 영향 분석을 한다

## 정리 (squash)

`decisions/`에는 결정 대기 중인 ADR과 현재 결정의 근거가 되는 ADR만 남긴다.
`ARCHITECTURE.md`가 더 이상 링크하지 않는 `Accepted` ADR은 `archive/decisions/`로 옮긴다.
`bin/check-design.py`가 후보를 경고로 알려 준다. 큰 설계 변경을 마친 뒤에 정리한다.

archive는 지우지 않는다. 기각 이력이 같은 제안의 반복을 막는다. 하지만 설계 변경을 제안할 때가 아니면 읽지 않는다.

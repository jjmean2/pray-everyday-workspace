# design-harness 피드백

이 프로젝트에서 design-harness 규약이나 도구를 쓰다가 불편했던 점을 남긴다. 서비스 설계 문서가 아니다.
절차가 과했던 경우, 규칙이 모호했던 경우, 검사가 잘못 걸린 경우, 필요한 출력이 없었던 경우 등을 적는다.

- design-harness 이슈 트래커가 생기면 이슈로 올리고 행을 지운다
- 도구 쪽에서 반영되면 행을 지운다
- 불편해도 도구가 업데이트되기 전까지는 현재 규약을 따른다

| 날짜 | 상황 | 불편했던 점 | 제안 (선택) |
|---|---|---|---|
| 2026-10-17 | 템플릿이 바뀌면 기존 문서를 모두 마이그레이션해야 하는지 검토 | 규약 변경의 종류와 문서 종류별 처리 규칙이 규약에 없다. 지금은 "규약 버전이 바뀌면 마이그레이션"만 있어서, `update`가 어떤 변경을 마이그레이션 없이 받아도 되는지 기준이 없다 | 변경을 셋으로 나눈다. **형식 변경**(헤더 필드, 상태 값, 표의 열, 폴더 구조처럼 도구가 읽는 부분)은 규약 버전을 올리고 `migrate`. **권장 구조 변경**(새 절, 안내 문구)과 **절차 변경**(규칙)은 버전을 유지하고 마이그레이션하지 않는다. ADR 본문은 어떤 경우에도 마이그레이션하지 않는다(형식 변경 때도 헤더만). 현재 문서(ARCHITECTURE, REQUIREMENTS)의 권장 구조는 다음에 고칠 때 맞춘다. 규약 문서의 "규약 버전" 절과 ADR-0009 3번에 반영하고, 최소 CLI의 `update`가 이 구분을 따르게 한다 |
| 2026-10-17 | 첫 요구사항을 쓰며 템플릿의 예시 행(R-001)을 지움 | 템플릿 예시가 실제 ID 형식(R-001)을 써서 "ID 재사용 금지" 규칙과 부딪힌다. 예시를 archive로 옮겨야 하는지 애매했다 | 템플릿 예시는 ID 형식을 쓰지 않거나(`R-예시`) 주석으로 둔다 |
| 2026-10-17 | 보류한 기능을 요구사항 표에 올림 | 보류 항목도 `미분석`이면 `check`가 매번 "영향 분석 필요"를 안내해서 진짜 분석이 필요한 항목이 묻힌다 | `보류` 상태의 `미분석`은 안내하지 않거나 따로 묶어 보여 준다 |
| 2026-10-17 | 첫 아키텍처를 씀 | 아직 정하지 않은 것(서버 DB, 폴더 구조, 열린 정책)을 둘 곳이 템플릿에 없다. 결정 표에 넣으면 결정처럼 보이고, 빼면 사라진다 | ARCHITECTURE 템플릿에 "아직 정하지 않은 것" 절을 둔다(결정이 아님을 명시) |
| 2026-10-17 | 웹 의존성 설치 | (불편이 아니라 참고) pnpm 12는 패키지에 포함된 에이전트 skill(`skills/**/SKILL.md`)을 `pnpm approve`로 승인받아 설치한다. TanStack Start가 라이브러리 버전에 맞춘 skill을 함께 배포한다 | ADR-0009의 배포 방식(skill 설치 위치, 어댑터) 검토 때, 패키지 매니저가 skill을 배포하는 경로를 대안으로 비교한다 |

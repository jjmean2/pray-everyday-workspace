# 설계 리뷰 체크리스트

변경된 코드와 문서가 현재 유효한 설계에서 벗어나지 않았는지 검토하는 절차다. 어떤 에이전트나 사람이 리뷰하든 이 문서를 따른다.
버그나 코드 스타일이 아니라 **현재 설계와의 정합성**만 본다. 리뷰어는 수정하지 않고 보고만 한다.

## 절차

1. 리뷰 대상 diff를 확인한다. 별도 지정이 없으면 `git diff HEAD`로 커밋되지 않은 변경을 본다.
2. 변경된 각 경로에 대해 `python3 scripts/check-design.py context <경로>`를 실행하고, 출력된 `ARCHITECTURE.md`를 모두 읽는다. 해당 스코프의 `friction-log.md`도 읽는다.
3. `python3 scripts/check-design.py`를 실행해 문서 정합성 결과를 참고한다.
4. 아래 항목을 점검한다.

구속력은 `ARCHITECTURE.md`와 `REQUIREMENTS.md`에만 있다. ADR은 이유를 확인할 때만 읽는다. `archive/`는 읽지 않는다.

## 점검 항목

- **경계 위반**: 모듈 의존 방향이나 공개 인터페이스 규칙을 어겼는가
- **스코프 위반**: 하위 스코프의 변경이 상위 스코프의 규칙을 뒤집는가
- **불변식 위반**: 불변식을 깨뜨릴 수 있는 코드 경로가 생겼는가
- **숨은 우회**: 특정 케이스만을 위한 분기, 플래그, 중복 상태, 동기화 코드가 생겼는가
- **가정 위반**: "현재 유효한 결정"의 전제한 가정이 이 변경으로 더 이상 참이 아니게 되었는가
- **레거시 모방**: "이행 중인 레거시"에 적힌 코드의 패턴을 새 코드가 따라 했는가
- **정리 누락**: 레거시를 지웠는데 표의 행이 남아 있거나, 표에서 지웠는데 코드가 남아 있는가
- **문서 불일치**: 코드가 `ARCHITECTURE.md`에 없는 구조를 도입했는데 문서는 갱신되지 않았는가. 문서에 이력 서술("예전에는")이 들어갔는가
- **마찰 누적**: 이번 변경 영역의 결정에 마찰 로그 항목이 이미 쌓여 있는가

## 보고 형식

각 발견 사항마다:
- 위치 (파일:줄)
- 어떤 설계 요소(`D-ID`, 불변식, 경계, 스코프)와 어긋나는가
- 판단: `문서만 갱신하면 됨` / `코드를 설계에 맞게 고쳐야 함` / `레거시 정리 필요` / `설계 재검토 필요`

발견 사항이 없으면 그렇다고 짧게 말한다.
